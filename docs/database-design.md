# Database Design

## 1. Introduction

SIEM v1 uses SQLite as its persistent storage layer.

The database stores collected security events and generated alerts, allowing the system to retrieve historical activity, investigate suspicious behaviour, and provide information to the SOC dashboard.

The database is located at:

```text
siem/database/siem.db
```

## 2. Database Architecture

```text
             SIEM Pipeline
                   |
                   v
             Database Layer
                   |
          +--------+--------+
          |                 |
          v                 v
      Events Table      Alerts Table
          |                 |
          +--------+--------+
                   |
                   v
              FastAPI
                   |
                   v
             SOC Dashboard
```

The database layer is responsible for creating tables, inserting records, and retrieving event and alert information.

## 3. Events Table

The `events` table stores parsed Linux journal events.

| Column | Description |
|---|---|
| `id` | Unique event identifier |
| `timestamp` | Event timestamp in UTC |
| `hostname` | Host where the event originated |
| `process` | Process associated with the event |
| `pid` | Process ID |
| `severity` | Original journal priority value |
| `message` | Event message |
| `source` | Event source |

Each successfully parsed event is inserted into the database by the processing pipeline.

## 4. Alerts Table

The `alerts` table stores alerts generated by the detection engine.

| Column | Description |
|---|---|
| `id` | Unique alert identifier |
| `event_timestamp` | Timestamp of the triggering event |
| `alert_timestamp` | Timestamp when the alert was generated |
| `rule` | Detection rule identifier |
| `severity` | Assigned alert severity |
| `message` | Alert description |
| `hostname` | Host associated with the alert |
| `process` | Process associated with the alert |
| `fingerprint` | SHA-256 alert fingerprint |

Separating events and alerts allows the SIEM to retain original security activity independently of detection results.

## 5. Database Operations

The database module provides functions for managing and retrieving SIEM data.

| Function | Purpose |
|---|---|
| `create_database()` | Creates the database and required tables |
| `insert_event()` | Stores a parsed event |
| `insert_alert()` | Stores a generated alert |
| `recent_alert_exists()` | Checks for a matching recent alert |
| `get_events()` | Retrieves event records |
| `get_recent_events()` | Retrieves recent events |
| `get_recent_alerts()` | Retrieves recent alerts |
| `get_alerts_by_severity()` | Retrieves alert counts by severity |
| `get_event_counts()` | Retrieves event statistics |
| `get_alert_counts()` | Retrieves alert statistics |
| `get_event_activity()` | Retrieves hourly event activity |

## 6. Alert Deduplication

SIEM v1 implements alert deduplication to reduce repeated storage of matching alerts.

The alert manager generates a SHA-256 fingerprint using:

```text
rule | hostname | process | message
```

Before inserting a new alert, the database checks whether an alert with the same fingerprint already exists within the configured cooldown period.

**Current configuration:**

| Parameter | Value |
|---|---|
| Hash algorithm | SHA-256 |
| Cooldown period | 300 seconds |
| Storage | SQLite alerts table |

If a matching alert exists within the cooldown period, the new alert is suppressed.

## 7. Event Activity Statistics

The database provides hourly event activity statistics for the dashboard.

A recursive SQL query generates 24 hourly buckets, including hours with zero events.

This allows the dashboard to display a consistent 24-hour activity chart rather than only showing hours that contain events.

## 8. Data Access

The FastAPI layer retrieves database information through the database module.

The dashboard accesses this information through API endpoints rather than connecting directly to SQLite.

This keeps database operations separate from presentation logic.

## 9. Design Considerations

### Persistence

SQLite provides local persistent storage for events and alerts.

### Separation

Events and alerts are stored independently to distinguish collected activity from detection results.

### Querying

Dedicated database functions support recent activity, statistics, and dashboard visualisation.

### Extensibility

The database layer can be expanded as the SIEM introduces additional event types, detection capabilities, and investigation features.

## 10. Current Limitations and Future Improvements

Potential improvements include:

- Database indexing for frequently queried fields.
- Retention and archival policies.
- Database backup and recovery procedures.
- Improved query performance for larger event volumes.
- Additional investigation and correlation metadata.
- Migration to a more scalable database when required.

## 11. Database Status

**Current status:** SQLite storage implemented.

SIEM v1 supports persistent event and alert storage, recent record retrieval, severity statistics, hourly activity aggregation, and alert deduplication checks.
